## 一、背景与现状

### 1.1 现有推送链路（已修复，2026-11-25）

```text
Celery Beat（4 个定时任务）
   ├─ 每小时   crawl_all_sources        爬虫（与本模块无关）
   ├─ 每天08:00 push_daily_subscriptions 订阅日报 —— 目前是占位，不发任何消息
   ├─ 每天09:00 send_expiring_bid_daily   到期预警 —— 已实现，推企微群
   └─ 每天02:00 archive_expired_bids      归档过期标讯 —— 只改数据库状态，不发消息
                    ↓
        wecom_push.py（企业微信群机器人 Webhook，.env WECOM_WEBHOOK）
```

- worker 任务注册问题已修复（`celery_app.py` 补 `include`），定时任务真实生效。
- 通道现状：**只有企微群机器人一个真实通道**（发到固定群）；邮件通道是骨架（print 占位）；`PushRecord` 推送日志表已建但**无接口无页面**。

### 1.2 现有数据表（与推送相关）

| 表                                                    | 现状                                   | 与本模块关系               |
| ---------------------------------------------------- | ------------------------------------ | -------------------- |
| `push_record` 推送日志                                   | 有模型，无接口无页面                           | 作为本模块「推送记录」的数据源，需补字段 |
| `bid_subscribe` 订阅                                   | 有接口有页面（订阅管理），字段：关键词/地区/行业/公告类型/频率/渠道 | 「订阅用户管理」直接复用并增强      |
| `bid_info` 标讯                                        | 完整                                   | 临时推送选标讯、订阅匹配的数据源     |
| `dict_notice_type` / `dict_region` / `dict_industry` | 完整                                   | 筛选与匹配的字典             |
| `sys_user` 用户                                        | 完整                                   | 订阅归属、后台操作人           |

## 二、关系书（数据关系设计）

### 2.1 新增表：`push_template` 推送模板

> 解决定时推送「模板可改、可预览、不用改代码」。

| 字段          | 类型                 | 说明                                                                                       |
| ----------- | ------------------ | ---------------------------------------------------------------------------------------- |
| id          | int PK             |                                                                                          |
| code        | varchar(32) UNIQUE | 模板编码，固定三个：`daily_summary`（每日推送）、`expiring_alert`（到期预警）、`archive_notice`（归档通知，已定 Q3=**发**） |
| title       | varchar(255)       | 消息标题（企微 markdown 的 `## 标题`）                                                              |
| content     | text               | 模板正文，支持变量占位符 `{var}`                                                                     |
| variables   | varchar(500)       | 该模板可用变量清单（逗号分隔，供前端编辑器提示用）                                                                |
| enabled     | tinyint            | 1 启用 / 0 停用（停用后该定时任务到点**跳过不发**）                                                          |
| updated\_by | int                | 最后修改的后台用户 id                                                                             |
| updated\_at | datetime           |                                                                                          |

**模板变量（每个模板允许用的）**：

| 模板              | 可用变量                                                             | 说明                                |
| --------------- | ---------------------------------------------------------------- | --------------------------------- |
| daily\_summary  | `{date}` `{count}` `{top_keywords}` `{top_regions}` `{bid_list}` | 对应现有 `send_bid_daily_summary` 的数据 |
| expiring\_alert | `{date}` `{count}` `{bid_list}`                                  | bid\_list 为「标题链接 + 截止时间」列表        |
| archive\_notice | `{date}` `{count}` `{bid_list}`                                      | 已定 Q3=发：每日归档汇总（归档条数 + 标讯列表）                |

### 2.2 扩展表：`push_record` 推送日志（加字段）

现有字段够用大半，补充：

| 加的字段         | 类型          | 说明                                                          |
| ------------ | ----------- | ----------------------------------------------------------- |
| push\_type   | varchar(16) | `scheduled` 定时 / `manual` 临时 / `test` 测试 / `subscribe` 订阅匹配 / `ai` AI 生成 |
| template\_id | int, 可空     | 关联 `push_template.id`（test/scheduled 有；manual/subscribe/ai 可空）                       |
| operator\_id | int, 可空     | 操作人（临时推送/测试推送/AI 推送的后台用户）；定时任务为 NULL                                    |
| preview      | tinyint     | 1 = 预览记录。已定 Q6=**落库**（预览也写记录，推送记录页默认筛掉 preview=1，可开关显示）                 |

> 现有字段复用：`bid_ids`（本次推的标讯）、`channel`、`recipient`、`subject`、`status`（0 成功 1 失败）、`error_msg`、`push_time`。
> `user_id` 目前 NOT NULL —— 已定 Q5：改为 nullable，配合 push\_type 区分。

### 2.3 实体关系

```text
push_template 1 ──── N push_record（定时/测试推送引用模板）
bid_subscribe 1 ──── N push_record（订阅推送时记录 subscribe_id）
bid_info     M ──── N push_record（通过 bid_ids 逗号分隔，不建中间表）
sys_user     1 ──── N bid_subscribe（订阅归属）
sys_user     1 ──── N push_record（operator_id 操作人，可空）
```

### 2.4 订阅匹配关系（核心规则）

一条订阅 `bid_subscribe` 推哪些标讯 = **按订阅自己的筛选条件匹配**，不是全类型都推：

```text
bid_subscribe                          bid_info
├─ keyword        ──LIKE──▶  title（多词按 空格/逗号 拆，已定 Q1：OR 命中任一词即推）
├─ region_code    ──等值──▶  region_code
├─ industry_id    ──等值──▶  industry_id
├─ notice_type_id ──等值──▶  notice_type_id
└─ 额外约束：status=1（已发布）、publish_time > last_push_at（只推新标的）
```

- 某字段为 NULL/空 = 该维度不约束（全匹配）。
- 匹配命中的标讯 → 套用**该订阅用户的推送内容格式**。
- 已定 Q2 = **C：本期只做管理界面（列表/匹配预览/条件编辑/记录），发送通道后接**；后期为订阅用户接专用企微机器人，届时只改通道层不动业务逻辑。U3/U4 的「立即推送」本期点击后生成推送记录并标记「通道待接入，未实际发送」。
- 频率 `frequency`：daily 每日汇总推 / realtime 触达即推；已定 Q7：hourly 本期不启用（下拉置灰）。

### 2.5 定时任务与模板的绑定关系

| Celery 任务                  | 时间       | 绑定模板 code        | 本模块要做的改造                                           |
| -------------------------- | -------- | ---------------- | -------------------------------------------------- |
| push\_daily\_subscriptions | 每天 08:00 | `daily_summary`  | 从占位改为真实实现：读模板 → 取昨日新增标讯 → 渲染 → 推群 → 落 push\_record |
| send\_expiring\_bid\_daily | 每天 09:00 | `expiring_alert` | 改为读模板渲染（现在是代码里拼字符串，改模板不生效的问题就在这）                   |
| archive\_expired\_bids     | 每天 02:00 | `archive_notice`（已定 Q3=发） | 改造：归档完成后读 `archive_notice` 模板渲染归档汇总 → 推群 → 落 push\_record（push\_type=scheduled） |

> **关键设计**：三个任务执行时**从数据库读模板**（不是读代码里的字符串），这样你在后台改完模板，第二天到点就按新模板发，无需重启服务。

## 三、功能书（页面与功能规格）

后台左侧菜单新增一级菜单「**推送管理**」，下挂三个页面 + 公共的推送记录：

```text
推送管理
├─ 定时推送    /push/scheduled
├─ 临时推送    /push/manual
├─ 订阅用户    /push/subscribers
└─ 推送记录    /push/records      已定 Q8：独立页面
```

### 3.1 定时推送页（/push/scheduled）

**布局**：三个模板卡片（每日推送 / 到期预警 / 归档通知），每张卡片显示：名称、绑定的执行时间、启用状态、上次执行时间与结果、操作按钮。

**功能**：

| #  | 功能    | 说明                                                                                       |
| -- | ----- | ---------------------------------------------------------------------------------------- |
| S1 | 模板编辑  | 点「编辑」打开抽屉：标题 + 正文 textarea + 变量插入按钮（点变量自动插入 `{var}` 到光标处）+ 恢复默认按钮                        |
| S2 | 实时预览  | 编辑器右侧（或下方）实时渲染预览：**用真实数据**（最近一条/当日数据）填充变量，模拟企微群里的最终效果（markdown 渲染样式，卡片气泡样式）              |
| S3 | 测试发送  | 「测试发送」按钮：按当前编辑内容 + 真实数据渲染，**真实发一条到企微群**（带「这是测试消息」前缀），发送结果写 push\_record（push\_type=test） |
| S4 | 保存    | 保存模板到 push\_template，记录 updated\_by/at；校验：变量必须在允许清单内（防写错变量名发出 `{xxx}` 原文）                |
| S5 | 启用/停用 | 停用后对应定时任务到点**跳过**（在任务开头检查 enabled，不发不报错），卡片上明确显示停用状态                                     |
| S6 | 执行历史  | 卡片可展开看该模板最近 N 次执行记录（时间、状态、条数、失败原因）                                                       |

**权限**：`push:template:edit`（admin、ops）。

### 3.2 临时推送页（/push/manual）

**两种模式（tab 或单页两块）**：

**模式 A：选标讯推送**

| #  | 功能     | 说明                                                                          |
| -- | ------ | --------------------------------------------------------------------------- |
| M1 | 标讯筛选选择 | 筛选器（关键词、公告类型、地区、行业、发布时间范围）+ 列表勾选多条（复选框），支持全选当前页                             |
| M2 | 组织消息   | 已选标讯列表可拖动排序/删除；消息格式提供两个预设（纯文本列表 / markdown 带链接卡片）；可加一段自定义开头文字               |
| M3 | 预览     | 同 S2 的真实效果预览（含长度校验：企微 markdown 上限 4096 字节，超限红色提示并禁止发送）                      |
| M4 | 发送     | 二次确认弹窗（显示目标群、条数）→ 发送 → 落 push\_record（push\_type=manual，operator\_id=当前管理员） |
| M5 | 失败处理   | errcode != 0 或超时时，记录 error\_msg，页面顶部提示，可重试（重试新建一条记录，不覆盖）                    |

**模式 B：自由文本通知（借用通道发通知）**

| #  | 功能              | 说明                                             |
| -- | --------------- | ---------------------------------------------- |
| M6 | 纯文本/Markdown 编辑 | 一个大 textarea，支持 markdown 预览；无标讯关联（bid\_ids 为空） |
| M7 | 常用通知模板       | 已定 Q9=**要**：3~5 个内置文案（系统维护通知 / 节假日调整等），一键插入可改            |
| M8 | 预览 + 发送         | 同 M3/M4                                        |

**权限**：`push:manual:send`（admin、ops）。

### 3.3 订阅用户页（/push/subscribers）

> 基于现有「订阅管理」页增强，现有页面已具备：关键词/状态筛选、启停、删除。

**新增功能**：

| #  | 功能        | 说明                                                                                                                     |
| -- | --------- | ---------------------------------------------------------------------------------------------------------------------- |
| U1 | 订阅条件列展示   | 表格列：用户、关键词、地区、行业、公告类型、频率、渠道、状态、上次推送（已定 Q10：最近命中数**不放列表列**，只在 U2 抽屉里显示）                                                                  |
| U2 | 匹配预览（核心）  | 每行「预览」按钮 → 抽屉展示**按该订阅条件当前能匹配到的标讯**（如近 7 天命中 12 条，列表列出），让管理员直观看到这个用户会收到什么——对应你说的「不能什么都推」的可视化确认                          |
| U3 | 手动触发单用户推送 | 「立即推送」按钮：按该订阅条件实时匹配（不限 last\_push\_at），套用订阅日报格式推给该用户，落 push\_record（push\_type=subscribe，subscribe\_id=该订阅 id）；二次确认防误点 |
| U4 | 批量推送（可选）  | 已定 Q11=**要**：「按频率分组批量立即推送」按钮，二次确认（输入确认词）防误触；本期点击生成记录并标记「通道待接入」                                                                                            |
| U5 | 条件编辑      | 管理员可直接改某条订阅的筛选条件（现有页面只读 + 启停）                                                                                          |
| U6 | 会员限制联动    | 已定 Q12=**做**：显示用户所属会员套餐与 `max_subscribe` 上限，超限标红提示（只读提示，不强制删除）                                                                        |

**权限**：`push:subscribe:view`（admin、ops）、`push:subscribe:push`（admin）。

### 3.4 推送记录（公共）

- 每个页面内嵌「最近推送」区块，或独立页面（Q8）。
- 列：时间、类型（定时/临时/测试/订阅）、模板、操作人、通道、内容摘要、目标、条数、状态、失败原因。
- 筛选：类型、状态、时间范围、操作人。
- 只读，不可删（作为审计）。

### 3.7 AI 智能生成推送（新增，2026-11-26 你补充的需求）

> 原话：「我和 AI 说，然后他能自己帮我生成需要推送的东西，这个 AI 要能调用标讯」。

**定位**：临时推送页内新增「AI 生成」入口（tab C，或独立弹窗——实施按 tab C 做），生成结果**回到临时推送的预览/发送管道**，AI 本身不直接发群。

**交互流程**：

| # | 步骤 | 说明 |
|---|---|---|
| A1 | 对话输入 | 管理员用自然语言描述需求，例：「找最近 3 天杭州的医疗器械中标公告，整理成推送文案，突出中标金额」 |
| A2 | AI 调用标讯检索 | AI 通过 **function calling 调用标讯查询工具**（复用现有 `ai_search` 检索能力/数据库直查），拿到命中的标讯列表（标题、公告类型、地区、截止时间、链接） |
| A3 | 生成推送内容 | DeepSeek 按需求产出 markdown 推送文案（可要求包含所选标讯链接），返回：文案 + 引用的 bid_ids |
| A4 | 预览 | 渲染到同 S2 的企微效果预览，**允许人工编辑改文案**（AI 产出是初稿，人可改） |
| A5 | 发送 | 走临时推送同一发送管道（20 条上限、4096 字节校验、二次确认），落 push_record（push_type=`ai`，operator_id=操作人，bid_ids=AI 引用的标讯） |

**约束**：
- AI 只读标讯数据，不写库、不直接发送——**必须经人工预览确认后由人点发送**（防 AI 误发）。
- 检索走 `content_text` 索引字段，**严禁 SELECT `content` 大列**（性能硬规则，列表接口同理）。
- 对话上下文只在单次会话内保持，不落库（对话记录本期不存，只存最终发送记录）。

**技术要点**：复用 `backend/app/services/deepseek_match.py` / `ai_search.py` 已有的 DeepSeek 调用与 function calling 模式；接口提供「标讯检索」一个工具即可（输入关键词/地区/时间范围，输出标讯列表 JSON）。
